# Research — Sitio web de marketing MVP (Logibienes)

Todas las incógnitas de `Technical Context` quedan resueltas aquí; no queda ningún `NEEDS CLARIFICATION` pendiente hacia Fase 1.

## 1. Framework

- **Decision**: Next.js 15, App Router.
- **Rationale**: SSR/SSG nativo por ruta (cumple Constitución I sin esfuerzo extra), Metadata API + `sitemap.ts`/`robots.ts` de primera clase (cumple Constitución IV), despliegue sin fricción en Vercel, `next/font` resuelve auto-hosting de Inter/Anton sin request externo.
- **Alternatives considered**:
  - **Astro** — igual de fuerte en SSR-por-defecto y probablemente más liviano para un sitio mayormente estático; se descarta solo porque el ecosistema de Metadata/JSON-LD de Next ya cubre el caso 1:1 y evita introducir una segunda herramienta de aprendizaje. Si el proyecto migra a un blog pesado en contenido (Fase 2), reevaluar Astro no está descartado.
  - **HTML estático a mano** — se descarta: 13 páginas con metadata/JSON-LD repetido a mano es más propenso a error que el ruteo por archivos de Next.

## 2. Estilos

- **Decision**: Tailwind CSS con tokens de marca (`#0E1F3C`, `#121417`, `#F4F6F8`, `#2D5BFF`) como `theme.colors` custom.
- **Rationale**: Cumple Constitución V sin CSS-en-JS ni arquitectura de estilos separada; los tokens quedan en un solo lugar (`tailwind.config`).
- **Alternatives considered**: CSS Modules — descartado, mismo resultado con más archivos y más repetición de valores hex.

## 3. Motion

- **Decision**: Framer Motion para scroll-reveal y transiciones de página; CSS puro (`transition`) para hovers simples de botones.
- **Rationale**: Framer Motion expone `useReducedMotion()` — necesario para el requisito no negociable de `prefers-reduced-motion`. CSS puro para micro-interacciones evita cargar JS donde no aporta.
- **Alternatives considered**: Animaciones 100% CSS con `@scroll-timeline`/IntersectionObserver a mano — descartado, reinventa lo que Framer Motion ya resuelve con mejor soporte de navegadores hoy.

## 4. Tipografía

- **Decision**: `next/font/google` para Inter (cuerpo) y Anton (titulares) — decisión de branding ya confirmada por el usuario (Anton en vez de Impact literal).
- **Rationale**: Auto-hosted en build time → cero request externo a Google Fonts en runtime, cero layout shift. Relevante también para agentes/crawlers con timeout corto (menos requests externos en el critical path).
- **Alternatives considered**: `<link>` a Google Fonts CDN — descartado, agrega una dependencia de red de terceros justo en el contenido que FR-008 exige que esté disponible sin fricción.

## 5. Formulario de contacto / captura de leads

- **Decision**: Un único Route Handler (`app/api/leads/route.ts`) que acepta tanto `application/json` (envío por `fetch`, camino con JS) como `application/x-www-form-urlencoded` (`<form method="post">` nativo, camino sin JS — cumple el edge case de `spec.md` y la Constitución I). Valida el payload (zod), aplica honeypot + una verificación de **tiempo mínimo de llenado** (no un límite de tasa por IP), captura consentimiento Habeas Data (FR-015), y envía un correo de notificación vía **Resend**. Sin persistencia en base de datos.
- **Rationale**: FR-004 exige una confirmación real de envío (no solo un `mailto:`, que no garantiza entrega ni confirmación) y FR-014 exige protección anti-spam sin CAPTCHA visual **y sin penalizar a un agente legítimo** — ambos requieren lógica de servidor mínima. No se justifica una base de datos (Constitución II) porque no se pidió panel de leads ni reportes en este MVP: el correo entrante (con el texto del consentimiento aceptado, su versión y fecha incluidos en el cuerpo) es la "persistencia" suficiente para el volumen esperado y sirve como evidencia de autorización para FR-015.
- **Camino sin JS — destinos FIJOS, nunca derivados del cliente**: cuando la Route Handler recibe `form-urlencoded`, hay exactamente dos destinos posibles por `tipo`, elegidos así: (1) éxito real → `303` a `/contacto/gracias` o `/propiedades/gracias`; (2) descarte silencioso de honeypot/timing-rápido-con-firma-válida (bot instantáneo) → responde **exactamente igual que el éxito**, `303` al mismo `*/gracias`, para no delatar la defensa; (3) falla de validación real, **o** formulario expirado (firma inválida, o válida pero con más de 2h desde el render — nunca tratado como éxito silencioso, sería una confirmación falsa a un visitante real que tardó), **o** fallo real de *envío* (Resend caído) → `303` a `/contacto/error` o `/propiedades/error`. Estos cuatro destinos son literales en el código de la Route Handler — **el valor de `paginaOrigen` que envía el cliente nunca se usa para construir un `Location` con un valor libre** (evita el open-redirect que señaló el arquitecto: un `Location` derivado de un campo controlado por el cliente es CWE-601); cuando `tipo` no es utilizable (ausente o fuera de enum), `paginaOrigen` ya normalizado sí decide entre los dos literales `/contacto/error` / `/propiedades/error` mediante un `switch` cerrado, lo cual no reabre el open-redirect. `paginaOrigen` viaja en el payload validado contra un enum cerrado (`"/contacto" | "/propiedades"`) — un valor fuera de ese enum, o su ausencia, se normaliza a `"desconocido"` (que cae a `/contacto/error` como default). El camino JSON conserva la respuesta `{ok, error}` para que el cliente pinte el mensaje inline sin recargar.
- **Renderizado dinámico en `/contacto` y `/propiedades`**: ambas rutas se marcan `export const dynamic = "force-dynamic"` (sin caché de CDN) porque `formTimestamp` debe reflejar el momento real de cada request — bajo SSG o una respuesta cacheada, `formTimestamp` sería una constante de build y la verificación de tiempo mínimo quedaría siempre inerte. Es el único costo de TTFB aceptado en el plan (el resto del sitio permanece estático); se declara explícitamente para que nadie lo revierta "optimizando" estas dos rutas a estático.
- **Anti-spam sin rate-limit por IP**: en vez de un límite de tasa (que exigiría un almacén compartido — Redis/KV — en contra de la Constitución II, y que puede bloquear agentes que comparten IP de salida con su proveedor), se usa (a) un campo honeypot oculto — ver §10 para la técnica exacta de ocultamiento, que es una excepción declarada a la regla general de "sin estado inicial oculto" — con `aria-hidden="true"`, `tabindex="-1"`, `autocomplete="off"` y sin `label` visible ni accesible que lo describa (para que un agente que lee por etiquetas jamás lo encuentre ni lo llene), y (b) un campo `formTimestamp` + `formTimestampSig` (epoch ms + firma HMAC-SHA256 de `String(formTimestamp)`, calculada por el servidor con un secreto no expuesto al cliente, `LEADS_HMAC_SECRET`) inyectados al renderizar la página. La Route Handler recalcula el HMAC y aplica dos umbrales con tratamiento distinto (ver `contracts/api-leads.md` "Ventana de validez"): firma válida + envío en menos de 1.5s → descarte silencioso (bot instantáneo); firma inválida o expirada tras 2 horas → error **visible**, no silencioso, porque puede tratarse de un visitante real que tardó, y tratarlo como éxito violaría el edge case de `spec.md` de nunca dar una confirmación falsa. La ventana máxima de 2 horas es lo que cierra el replay: sin ella, un bot que hace un solo GET previo podría reutilizar el mismo par firmado para envíos ilimitados indefinidamente. **Precisión importante**: `formTimestamp` en sí sigue viajando en texto plano en el HTML — lo que no se puede forjar sin conocer el secreto es la *firma*, no el timestamp. Ninguno de los dos campos requiere almacén compartido — el secreto es una variable de entorno del servidor, no estado por request.
- **Alternatives considered**:
  - **Formspree/servicio de formularios de terceros** — descartado: menos control sobre copy de confirmación, honeypot y el camino sin JS; una dependencia externa más sin necesidad.
  - **Solo enlace `mailto:`/WhatsApp** — descartado como *único* canal porque no cumple FR-004 (confirmación) ni FR-015 (consentimiento registrado); se mantiene como **CTA primario de baja fricción** (FR-003, vía el componente `contact-cta.tsx` compartido) en paralelo al formulario, no en su reemplazo — y como *fallback* explícito si el envío del formulario falla.
  - **Base de datos + dashboard de leads** — descartado por ahora: no hay requisito de spec que lo pida; se reevalúa si el volumen de leads justifica un panel (ver Fase 3 de `ARQUITECTURA-WEB.md`).
  - **Límite de tasa por IP con Redis/Upstash/Vercel KV** — descartado: introduce un almacén externo que tensiona la Constitución II sin que ningún FR lo pida explícitamente, y un límite por IP puede bloquear a un agente de IA legítimo saliendo por una IP compartida de su proveedor. Riesgo residual aceptado y su mitigación de plataforma: ver `plan.md` §"Guardas antes de producción".
  - **Redirect a la página de origen con `?error=...`** — descartado: además del riesgo de open-redirect si se deriva de `paginaOrigen`, crea variantes de URL indexables por accidente (tensiona la Constitución IV); se prefieren rutas `*/error` fijas y `noindex`.
- **`avisoVersion` no se confía al cliente**: el cliente puede enviar el campo, pero la Route Handler siempre lo sobreescribe con la constante vigente de `content/legal.ts` (`AVISO_PRIVACIDAD_VERSION`) antes de registrarlo como evidencia — igual que `fecha`, es un dato que solo tiene valor probatorio si lo fija el servidor, no el cliente.
- **Supuesto pendiente (`AS-02`)**: Resend requiere que el usuario cree una cuenta y verifique un dominio remitente por DNS antes de producción; hasta entonces se usa el modo sandbox de Resend en desarrollo. No confirmado aún por el usuario — ver resumen final de `logiplan`.

## 6. Hosting

- **Decision**: Vercel.
- **Rationale**: Cero configuración para Next.js, CDN global (ayuda a SC-003/TTFB para agentes con timeout corto), previews automáticos por rama — útil para que el usuario revise cada fase de `tasks.md` antes de fusionar.
- **Alternatives considered**: Netlify — funcionalmente equivalente para este caso; se prefiere Vercel por integración de primera clase con Next.js (menos configuración manual de runtime).

## 7. Verificación de accesibilidad para agentes de IA

- **Decision**: Playwright + `axe-core` para violaciones WCAG 2.2 AA automatizadas, un smoke test dedicado que hace `fetch()` crudo (sin ejecutar JS) a cada ruta pública y verifica que el contenido esperado (h1, CTA de WhatsApp/contacto, texto de FAQ) está presente en el HTML devuelto, **más una pasada manual con lector de pantalla real** (NVDA o VoiceOver) sobre el flujo completo del formulario de contacto.
- **Rationale**: axe-core y el smoke test verifican mecánicamente FR-008/FR-009 y SC-003/SC-005. Ninguno de los dos verifica SC-004 ("una persona con lector de pantalla completa el formulario de principio a fin") — eso es un chequeo de *flujo operable*, no de estructura estática, así que se declara explícitamente como paso manual de cierre de fase, no se finge cubierto por axe-core.
- **Alternatives considered**: Solo Lighthouse CI — se mantiene como chequeo adicional de Performance/SEO, pero no valida "contenido presente sin JS" (Lighthouse sí ejecuta JS al auditar) ni SC-004.

## 8. `robots.txt` — política por defecto vs. allowlist enumerada

- **Decision**: Política base permisiva — `User-agent: *` / `Allow: /` / `Disallow: /api/` — más líneas explícitas confirmando acceso a los user-agents de navegación/respuesta en vivo conocidos hoy: `GPTBot`, `ChatGPT-User`, `OAI-SearchBot`, `ClaudeBot`, `Claude-User`, `Claude-SearchBot`, `PerplexityBot`. `Google-Extended` y `Applebot-Extended` se documentan aparte como **tokens de opt-out de entrenamiento** (no crawlers que piden páginas) — se listan como señal de política, no como mecanismo de acceso.
- **Rationale**: Una allowlist enumerada sin una regla base permisiva dejaría fuera, por omisión, a cualquier agente nuevo no listado — exactamente lo que FR-011 quiere evitar. La regla base cubre el espíritu del requisito; la enumeración es refuerzo explícito para los agentes hoy más relevantes.
- **Alternatives considered**: Solo la allowlist enumerada (sin regla base) — descartada, es la causa de gap señalada por el arquitecto: frágil ante cualquier agente no anticipado.

## 9. JSON-LD — qué campos NO se publican todavía

- **Decision**: El `Organization`/`RealEstateAgent` del layout raíz publica únicamente `addressLocality: "Medellín"`, `addressRegion: "Antioquia"`, `addressCountry: "CO"`. Los campos `telephone`, `email` y `sameAs` se **omiten por completo** del JSON-LD (no se rellenan con el placeholder) hasta que existan datos reales y se resuelva `AS-01`.
- **Rationale**: Constitución III — un placeholder en `telephone`/`email` publicado en datos estructurados es exactamente "dato inventado presentado como real" para cualquier consumidor de máquina (buscador, agente de IA), con más peso que un placeholder visual porque los sistemas automatizados tratan JSON-LD como fuente de verdad.
- **Alternatives considered**: Publicar el placeholder marcado con un valor obviamente falso (ej. `"+57 000 000 0000"`) — descartado: no hay garantía de que un consumidor automatizado distinga "obviamente falso" de un dato real.

## 10. Motion y estado inicial del contenido

- **Corrección sobre la primera versión de esta decisión**: la primera versión asumía que el `initial` de Framer Motion "no existe en el HTML crudo servido". Es falso — Framer Motion **sí** emite el estilo de `initial` como `style` inline durante el SSR (es su comportamiento documentado, para evitar parpadeo en el cliente). Un `<motion.div initial={{opacity:0}} whileInView={{opacity:1}}>` produce literalmente `style="opacity:0"` en el HTML servido — exactamente el problema que esta sección pretendía evitar, y el smoke test de "fetch sin JS" **no lo detecta** porque el texto sigue presente en el DOM (solo invisible).
- **Decision (corregida)**: (1) Contenido de página: ningún contenedor de contenido usa el `initial` de Framer Motion para ocultarlo. El patrón obligatorio es **"gating por montaje"**: el servidor y el primer render de cliente pintan el contenido en su estado final visible (sin wrapper de motion, o `motion.div` con `initial={false}`); solo después de montado (`useEffect`) un componente cliente activa la variante animada para revelarlo en el próximo scroll-into-view. Si JavaScript nunca corre, el usuario simplemente ve el contenido ya visible, nunca oculto. (2) El smoke test de "fetch sin JS" (ver `plan.md`, Testing) se extiende para fallar explícitamente si encuentra `opacity:0`, `visibility:hidden` o `display:none` en línea sobre cualquier contenedor de contenido del HTML crudo — así una regresión futura la detecta un test, no una revisión visual.
- **Excepción explícita: el campo honeypot**. La regla de "sin estado inicial oculto" es sobre *contenido*, no sobre el campo honeypot de §5/`contracts/api-leads.md`, que necesita ser invisible por diseño. Su ocultamiento usa una técnica distinta y acotada a ese único campo: `position: absolute; left: -9999px; width: 1px; height: 1px; overflow: hidden;` en línea (no una clase reutilizable, para que el smoke test de arriba no lo confunda con contenido oculto por error), **más `aria-hidden="true"` y `tabindex="-1"`** (necesarios aquí — a diferencia del contenido real, un `<input>` sin nombre accesible y sin `aria-hidden` dispara la regla de `label` de axe-core como violación crítica de WCAG 2.2 AA, lo que rompería SC-005; con `aria-hidden="true"` + `tabindex="-1"` el campo sale del árbol de accesibilidad y esa regla no aplica), sin `label` visible ni accesible, y `autocomplete="off"`. El smoke test de contenido se limita explícitamente a los `data-content` de las secciones reales, excluyendo este campo.
- **Rationale**: Es la regla concreta que hace cumplible la Constitución I frente al patrón más común de romperla (scroll-reveal con estado inicial oculto por CSS o por SSR de la librería de motion, invisible para un fetch sin JS o para un usuario con JS deshabilitado), sin bloquear el único caso legítimo de ocultar algo a propósito (el honeypot).
